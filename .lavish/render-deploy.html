02 The one that would have bitten you

This is the reason to read a deploy plan before running one.

Critical · data loss

schema.sql line 3 is a DROP TABLE

-- schema.sql:1-6
-- Bubble or Not — DDL (agents-README §6)
DROP TABLE IF EXISTS probe_cache, registry_edges, signatures, factor_results,
                     evidence, run_events, runs CASCADE;
CREATE TABLE runs(  -- 7 plain CREATE TABLE, 0 IF NOT EXISTS

The natural instinct when wiring a new Render service is to make the database self-bootstrapping — put psql -f schema.sql in the build or a preDeployCommand so a fresh deploy always has its tables. Doing that here wipes every stored run on every single deploy.

That is not just lost history. PLAN.md Pass 8 designates GET /state?run_id=<past-run> as your demo insurance — the replay URL you fall back to if the backend dies on stage. An auto-applied schema means that URL 404s after every deploy, and you would discover it at the worst possible moment.

Rule: schema.sql is a one-shot bootstrap. Apply it exactly once, by hand, via render psql. Never in build, never in pre-deploy, never on startup. If you later want idempotent boots, that is a separate change to CREATE TABLE IF NOT EXISTS with the DROP removed.

Why the browser never sees the API origin

A Render static-site rewrite is a server-side proxy, not a redirect. The browser requests /state from the static host; Render fetches it from the API and returns it. Same origin throughout, so there is no CORS preflight at all and api.ts needs no change.

Order matters: the SPA catch-all (/* → /index.html) must come last, or it swallows the API routes above it.

05 The one real design decision

Blocker 5 has two fixes. They are not equivalent — one touches three files and adds a failure mode, the other touches zero application code.

Recommended · static-site rewrites

Proxy the API through the static host

# render.yaml — bubble-web
routes:
  - type: rewrite
    source: /state
    destination: https://bubble-api.onrender.com/state
  - type: rewrite
    source: /events
    destination: https://bubble-api.onrender.com/events
  - type: rewrite
    source: /evidence/*
    destination: https://bubble-api.onrender.com/evidence/*
  - type: rewrite        # MUST be last
    source: /*
    destination: /index.html
  • Zero application code changes. api.ts and api.py untouched.
  • CORS becomes irrelevant — one origin, no preflight, nothing to misconfigure.
  • /fixtures/* keeps resolving locally, so the offline fallback in useDashboardData.ts:78 still works when the API is down.
  • Each service keeps its native runtime — Node builds the SPA, Python runs the API. No single image needing both.

Unverified: that Render rewrites accept an absolute external destination. I cannot confirm this without a live deploy. If it rejects them, fall back to the right-hand option — a ~20 minute change, not a redesign.

Fallback · cross-origin

Absolute API base + CORS allowlist

// dashboard/src/api.ts
const BASE = import.meta.env.VITE_API_BASE ?? "";
function getJson(url) { fetch(BASE + url) }

# agents/api.py
allow_origins=os.environ["CORS_ORIGINS"].split(",")
  • Touches api.ts, api.py, and render.yaml — three files, one of them the contract boundary.
  • Adds a real failure mode: a wrong VITE_API_BASE is baked in at build time, so fixing it means a rebuild, not an env-var edit.
  • Every API call becomes cross-origin, so a CORS mistake is now a live demo failure.
  • Genuine upside: the API is directly reachable, which is marginally easier to curl and debug.

06 Deploy sequence

Nine steps. Amber = must be done by hand in the Dashboard. Red = destructive, exactly once, never automated.

  1. Fix the two code blockers edits

    Add asyncpg==0.30.0 to requirements.txt, and make config_version prefer RENDER_GIT_COMMIT before shelling out to git.

  2. Add render.yaml new file

    Full Blueprint below. Validate before pushing — this catches schema errors without burning a deploy.

    render blueprints validate ./render.yaml

  3. Create the private repo and push

    gh repo create bubble-or-not --private --source=. --remote=origin
git push -u origin main

    Confirm .env is absent from the push — it is gitignored, but verify with git ls-files | grep env before the repo exists anywhere remote.

  4. Create the Blueprint Dashboard — CLI can't

    Render Dashboard → New → Blueprint → pick the repo. It reads render.yaml and provisions all four resources. This is the one irreducibly manual step.

  5. Set the four secrets Dashboard

    Marked sync: false in the Blueprint, so Render prompts for them and never stores them in git: YOU_API_KEY, ANTHROPIC_API_KEY, FMP_API_KEY, ADMIN_KEY. DATABASE_URL is wired automatically from the database.

  6. Apply the schema — once, by hand destructive

    render psql bubble-db < schema.sql

    Then never run it again. Re-running drops every table and takes your replay URL with it. See §02.

  7. Verify the API alone, before the SPA

    curl -s https://bubble-api.onrender.com/healthz
# expect {"ok":true,"store":"PGStore"} — PGStore, not MemoryStore

    MemoryStore here means DATABASE_URL did not reach the app, and every run you do afterwards evaporates on restart.

  8. Seed one real run

    curl -X POST https://bubble-api.onrender.com/rescore \
  -H "X-Admin-Key: $ADMIN_KEY"

    Gives the page real data and gives you a run_id to bookmark as the Pass 8 replay URL.

  9. Walk the Pass 6 checklist

    The five boxes from PLAN.md, below. Do the 20-minute idle test before demo day, not on it.

08 Risks I can't retire from here

Memory on Starter

Starter is 512MB. yfinance pulls pandas + numpy, which are heavy resident. Add asyncpg's pool and FastAPI and it should fit — but if you see boot OOMs, that is the cause, not your code.

Rewrite destinations

The external-URL rewrite in §05 is the one unverified assumption in this plan. It is a 20-minute fallback if wrong, but it is the thing most likely to surprise us on the first deploy.

Region pinning

Postgres and the web service must share a region or the internal connection string won't resolve. Pin every resource explicitly rather than trusting defaults.
